What I found
● Good news: the automation works and the token is valid
The daily-attribution-brief GitHub Action runs Mon–Fri and last succeeded June 5. It uses the GHL_PIT repo secret, and its runs return real contact data (no auth errors) — so that token is fine. No re-auth needed for the daily brief to run.
● The bug: the brief counts your whole database, not yesterday
The contact pull keeps every record older than end-of-yesterday but never checks the start of the window, so it sweeps up your full history and stops at the 20-page × 100 = 2,000 cap. Receipt: June 2, 3 and 4 briefs are identical (2,000 / 0 / 0; source buckets sum to exactly 2,000). Real daily counts are never identical three days running.

The fix (needs one live test before trusting it)

In .github/workflows/daily-attribution-brief.yml, the get_contacts() function needs to actually bound to the day. The opportunities pull already does this correctly — contacts just needs to match it: only keep a contact when start ≤ dateAdded < end.

One caveat I won't paper over: GHL is currently ignoring the startAfter cursor and returning oldest-records-first, so a client-side date filter alone could swing the count from a wrong 2,000 to a wrong 0. The reliable fix is to switch the pull to POST /contacts/search with an explicit dateAdded range filter, sorted newest-first — then confirm against a day you know the real number for. That validation needs a working token, which is why this is a recommendation, not a change I made blind.
